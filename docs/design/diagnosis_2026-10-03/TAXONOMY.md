# AppWorld 失败诊断：错误分类（2026-10-03）

**数据**：discovery 50 个任务 × 6 次开 thinking 的 F0 评测（CC_F0_orig_seed1、CC_F0_fix_seed1、CC_T1_F0_disc_seed2–5）。
- 16 个任务有成有败，17 个每次都失败，17 个每次都成功。
- 诊断 33 个出现过失败的任务，每个任务最多看 3 次失败和 2 次成功，共 **93 次失败**。
- 诊断由 6 个 Claude 子 agent（强模型）完成，每个 agent 看一批任务的完整轨迹（代码、输出前 200 字符、推理末尾）。
- 各批的原始报告见本目录 `batch*.md`。下面的计数是我按各 agent 给出的错误代码汇总的，一次失败可以同时有多个代码。

## 0. 总体图景

- **93 次失败里，绝大多数是 30 步预算用完、根本没调用 `complete_task`**，而不是答错。完成了但答错的大约只有 12 次，而且其中多数是环境或 ground truth 本身的问题（见 §3）。
- **余量极小**：在有成有败的任务里，成功的那次通常在第 26–30 步才完成。浪费 1–3 步就会从成功变成失败。
- **成功和失败的分岔点几乎都是效率问题，而不是策略不同**：成功的那次会批量处理（用循环、一个 cell 里做多次调用），并且跳过不必要的文档查询和绕路。

## 1. 主要错误类别（按出现频率；分母为 93 次失败）

| # | 类别 | 出现次数 | 机制 | 前 15 步能否看出 | 在线检测方法（rubric 维度候选） |
|---|---|---|---|---|---|
| R1 | **逐个查文档，开销过大**（A） | ~65（70%） | 每次调用前单独查一次 API 文档；全部轨迹里 **55.4% 的 cell 是 api_docs**。模型在推理里直接引用系统提示中的 "always look at API specs before calling" 和 "one chunk per step" | 能：前 10 步里文档占比超过 40% | 代码：已用步数中文档调用的占比 |
| R2 | **推进太慢，预算耗尽**（I） | ~65 | R1、R3 等问题叠加的结果 | 部分：第 15 步时完成的子目标太少 | 代码：剩余步数 < 预计还需要的步数 |
| R3 | **harness 假执行**（J，不含环境问题） | ~45（48%） | 回复被截断，或者没有闭合的代码块；harness **悄悄执行**默认的 `show_app_descriptions()`、半截代码、`...` 占位符或推理里的散文，**并且不告诉模型**。最多一次连续 15–21 步。日志统计：一条轨迹的假执行步数为 0/1–2/3–5/≥6 时，胜率分别是 0.57/0.28/0.06/0.00 | 能 | 代码：harness 自己就能看到（没有闭合的代码块、执行的是默认代码、语法错误、`...` 占位符） |
| R4 | **逐个处理，不用循环**（G / per-item） | ~30 | N 个对象就花 N 步，每步代码只改一个字面量（搜索、加购物车、发邮件、打开 thread）。**这是有成有败任务里成功与失败最清楚的分界** | 有时 | 代码：连续两步调用同一个 API，只有字面量参数不同 |
| R5 | **API 用法错误**（B） | ~29 | 给公开的搜索 API 传 `access_token`；猜出不存在的 API 名（`add_to_cart`、`checkout`）；`page_limit` 超过 20；把密码硬编码 | 能 | 代码：执行报错文本，比如 "Unexpected parameter"、找不到 API |
| R6 | **API 列表显示被截断** | 多数多 app 任务中都有 | 大 app（gmail、amazon）的 `show_api_descriptions` 输出超过显示上限，导致反复重新列出，或者看不到需要的 API | 能 | 代码：同一个文档调用重复出现，或输出达到显示上限 |
| R7 | **歧义瘫痪，没有代码的空转**（E+G） | ~10 | 数据已经收齐，却对一个没说清楚的细节反复推理（比如 "including me" 怎么理解、CSV 行顺序、清空购物车算不算附带损害），连续 8–21 轮不输出代码。和 R3 叠加时，每一轮都被默认代码掩盖 | 能（连续多轮没有代码） | 代码：连续 ≥2 轮没有代码 |
| R8 | **用错数据源绕路**（D） | ~7，另外在很多轨迹中有 2–6 步的绕路 | 下单需要 amazon 自己的地址和卡的 ID，模型却去调用 supervisor 的 `show_addresses`/`show_payment_cards` | 能 | 代码：购物任务里调用了 supervisor 的地址或卡片接口 |
| R9 | **收尾时没有预算意识** | ~9 | 主要写操作已经完成，最后 1–3 步却去验证、重新查文档，甚至 `show_api_doc(complete_task)`，而不是直接调用 `complete_task` | 不适用（发生在收尾） | 代码：剩余 ≤3 步、写操作已成功，但下一步不是 `complete_task` |
| R10 | **结账前置条件到最后才以 422 暴露** | ~6 | 无效的优惠码（`promo_valid:false` 在第一次查看购物车时就能看到）、库存不足、卡里余额不足；暴露时剩下的步数已经不够补救 | 有时（相关字段早就可见） | 代码 + 提示：422 时把错误原因和补救方法展示出来 |
| R11 | **误读题意** | ~8 | "reach home" 被理解成每个受邀人的家；筛选条件漏掉了改过措辞的取消邮件 | 一般不能 | 语义（裁判） |
| R12 | **搜索只排序不过滤** | ~3 | gmail 的 query 只影响排序，任何关键词都返回整个收件箱（217 条） | 能 | 代码：不同 query 返回的总数相同 |

## 2. 有成有败的任务：成功和失败差在哪

- **批量处理**：f099b4c、8f79e35、953b296、c1091c7、3f3c139 里，成功的那次都把 N 个对象放进一个循环、一个 cell 里处理完。
- **跳过不必要的文档查询和绕路**：690d51b、e201314、a3ba388、4242c97、9871968。
- **出错后能立刻补救**：9871968，422 之后直接换下一张卡。
- **不做多余的回读**：9126bf0、09ac073。因为环境的回读不可靠（见 §3），回读反而会引发重复写入。
- **推理短、代码块小**：cdf61bd，这样不容易被截断。

## 4. 对下一步的含义（第 2 步：rubric 对齐错误；第 3 步：用 rubric 引导推理）

**A. 先修 harness 本身的 bug（属于基线修复，不算 rubric 干预）。** 这几项会混杂所有后续实验：
1. 没有闭合的代码块时，**不执行默认代码**，向模型返回明确的提示（"没有收到可执行的代码块，状态未改变"），并且**不计入 30 步预算**；
2. 只取**最后一个**闭合的代码块，拒绝 `...` 占位符；
3. 把 `max_tokens` 从 1024 调高到 2048 或 4096：开着 thinking 时，1024 经常不够写完代码；
4. `show_api_descriptions` 改为返回紧凑的名字列表，避免被截断。

改完之后要重新跑 F0，作为新的基线（F0′）。

**B. rubric 维度**，即 R1、R4、R5、R7、R8、R9、R10 的在线检测器，大部分可以直接用代码检测。检验标准有三条：
- 在失败轨迹上触发得明显多于成功轨迹；
- 在有成有败的任务内部也成立（6 次评测 × 16 个任务）；
- 在验证集 4 个 seed 上关联依然存在。

**C. 由 rubric 触发的干预**，每个维度对应一个 v3 编辑。检测器触发时，注入针对性的提示：
- R1："可以在一个 cell 里同时查多个 API 的文档；已经清楚的 API 不必再查；还剩 N 步"
- R4："用一个循环一次处理完剩下的所有项目"
- R9："还剩 N 步，现在就调用 complete_task"
- R5、R8：对应 API 的具体用法说明
- R7："按最自然的理解选定一种解读，直接执行"

在验证集上和 F0′ 做配对比较，每个编辑跑 2 个 seed × 50 题，按每类错误能解释的失败数排优先级。
